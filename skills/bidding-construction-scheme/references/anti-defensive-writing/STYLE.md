# 非防御性写作：工程、预算与交付适配

用于本技能产生的正文、项目特征、编制说明、图注、表格备注和最终答复。起草前读本文件，专业复核后再按末尾清单审查。用户指定的文体、完整范围、模板和内容深度优先。

## 写作顺序

1. 先给读者需要的结论或处理意见，紧接关键数据、图纸/条文依据及实际影响。较长报告可按“现状—原因—影响—处理—所需成果”组织，不按工具调用或失败尝试写流水账。
2. 主张的强弱应与证据匹配。可确定的内容直接说清；推算和暂估标出具体参数、数量影响、用途及更新条件。不要把“尚未找到”写成“图纸没有”。
3. 一段集中解释一个问题。优先用规格、位置、数量、因果和动作，让非专业读者能判断；保留服务于判断的技术细节。
4. 删除无关的自我辩解、重复的“仅供参考/不承担责任”、没人提出的假设性攻击和泛泛免责声明。确有影响的边界直接放在对应结论旁说明一次，不用多页重复免责。
5. 结尾归纳已经核实的结果和下一步具体动作。错误、失败检验、设计冲突、负面比较及必要限制按事实写明，不用弱化措辞掩盖，也不把一个局部问题放大成整体否定。

## 专业控制保持原样

- 不能为了叙事有利而删除用户要求的比较项、反面证据、缺陷、失败结果或不利费用；不能挑换比较口径、指标或分母来制造优势。
- 不能把预算值、条件量、未核节点写成已批准的施工/加工/采购数据。真实的待设计确认、待检测、暂估、不可执行条件应保留，并说明具体缺什么、影响什么、由谁落实。
- 保留原技能的模板保护、取证去重、计算公式、源文件追溯、审价与报价边界、危险源控制、质量验收和交付检查。文字审查不能越过失败的专业验收门槛。
- 不修改数量、价格、日期、单位、钢号、图号、标准条文、设备参数、试验结果或授权范围以换取“更好看”的结论。需要纠正数据时走原专业复核流程。
- 用户要求详细报告、施工工序、法规原文或完整清单时，不能以“去防御”为理由压缩成摘要。固定模板、合同文本、规范引用和证据原话保持准确。
- 对科研、软件评估或审价复核，仍应如实报告重要局限、未通过测试和不利结果；不得以只讲优势取代完整评价。

## 具体表达示例

空泛：“由于资料有限，本结果仅供参考，无法保证准确，最终以现场为准。”

具体：“设备基础钢筋按120 kg/m³暂估；混凝土体积取图示外形。预算包含该暂估量，采购时按设计配筋表更新。”

空泛：“此节点可能有问题，不代表图纸一定错误，建议有关单位进一步核实。”

具体：“同一M20连接，总视图孔25.5、剖面孔21.5。设计需分别标明两侧板孔径，工厂据统一制孔图加工。”

上述参数是表达示例，不是任何新项目的默认数值。固定法规用语、真实验收结论和用户要求的边界说明，不因含有“不能”“未通过”“暂估”而删除。

## 交付前文字审查

1. 首段是否直接回答当前请求？主结论后是否有位置、数据或可追溯依据？
2. 逐项对照原专业事实记录：数量、单位、规格、日期、出处、缺陷、适用条件和用户要求是否完整保留？重要失败或不利结果是否仍被如实表达？
3. 有无把过程日志写进正式正文、反复自证、泛泛免责或超出任务的假设性警告？只改这些表达，不删真实控制条件。
4. 每个确需确认的问题是否写清具体参数、影响与所需成果？同一边界是否在最适合的位置解释清楚？
5. 正式文件、摘要、表格和最终答复的结论是否一致？已完成、条件成立和未完成的工作有无混写？

可选只读检查：

```text
python scripts/review_prose.py <文字.md或.docx> --required-text <必须保留的关键事实> --output <已有QA目录/文字审查.json>
```

[检查器](../../scripts/review_prose.py)仅标记可能的套话和指定文本是否保留，不修改原文，不自动删句。匹配提示不是错误结论，人工根据上下文处理；“无提示”不证明技术正确。可用多个`--required-text`检查关键短语；不要把它当作完整语义审查。
